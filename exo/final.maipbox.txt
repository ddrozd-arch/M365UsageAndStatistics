🧩 PODSUMOWANIE — CAŁA ARCHITEKTURA OD A DO Z

1️⃣ Problem bazowy

Twoje API odpytuje EXO o FullAccess (Get-MailboxPermission).
Przy skrzynkach z dużą liczbą delegatów (np. 400) EXO:

• działa wolno,
• potrafi wisieć 30–120 sekund,
• powoduje timeouty po stronie API / IIS / HttpClient.


RunspacePool odpada — nie chcesz go używać.

---

2️⃣ Cel

Zbudować architekturę, która:

• nie timeoutuje,
• nie blokuje API,
• nie wymaga bazy danych,
• jest lekka,
• ma 4 równoległe workery,
• waliduje skrzynkę przed startem,
• zapisuje wyniki tylko do plików,
• czyści pliki raz dziennie,
• jest gotowa do implementacji w .NET 8.


---

3️⃣ Walidacja skrzynki przed utworzeniem joba

Najlepsza metoda: Microsoft Graph – mailboxSettings.

GET /users/{UPN}/mailboxSettings


Interpretacja:

• 200 OK → skrzynka istnieje w EXO
• 404 → literówka / skrzynka on-prem / brak licencji EXO
• 403 → brak licencji EXO
• 401 → brak uprawnień tokenu


Dlaczego to jest idealne?

• szybkie (1–2 ms),
• lekkie,
• nie wymaga EXO sesji,
• nie generuje throttlingu,
• pewnie wykrywa on-prem.


Worker nigdy nie dostaje joba dla skrzynki, która nie istnieje w EXO.

---

4️⃣ API — rola minimalna

API nie wykonuje EXO.
API robi tylko:

1. Walidację skrzynki przez Graph.
2. Tworzy job.
3. Zapisuje job do pliku.
4. Wrzuca job do kolejki.
5. Zwraca jobId.


API jest natychmiastowe → zero timeoutów.

---

5️⃣ Struktura joba

Idealny model:

{
  "id": "A7F3",
  "user": "dawid@firma.com",
  "name": "permissions for mailbox shared@firma.com",
  "created": "2026-07-08T20:33:00Z",
  "status": "Pending",
  "resultPath": "jobs/A7F3.json"
}


Pola:

• id — 4–8 znaków (Base32/Base36/small GUID)
• user — z HttpContext
• name — opis operacji
• created — timestamp
• status — Pending, Running, Completed, Failed
• resultPath — ścieżka do pliku z wynikiem


---

6️⃣ Kolejka jobów

Najlepsze rozwiązanie: Channel w .NET 8.

Dlaczego?

• thread-safe,
• szybkie,
• lekkie,
• idealne dla workerów.


---

7️⃣ Workery — 4 sztuki

Każdy worker:

• czeka na job,
• ustawia status = Running,
• tworzy sesję EXO V3,
• wykonuje Get-MailboxPermission,
• zapisuje wynik do pliku,
• ustawia status = Completed.


Czy worker obciąża zasoby, gdy nic nie robi?

Nie.

Worker jest „pusty”, dopóki nie dostanie joba.

Obciążenie pojawia się tylko podczas:

• tworzenia sesji EXO,
• wykonywania cmdletu,
• zapisu pliku.


4 workery to bezpieczna liczba dla EXO throttling.

---

8️⃣ Pliki zamiast bazy

Struktura katalogów:

/jobs
    A7F3.json
    B9D2.json
/jobhistory.json


Czyszczenie:

• raz dziennie o północy,
• albo po X godzinach.


To jest lekki, prosty i wystarczający mechanizm.

---

9️⃣ Endpointy API

`POST /mailbox/{id}/permissions`

• walidacja Graph
• tworzenie joba
• zapis joba
• wrzucenie joba do kolejki
• zwrot jobId


`GET /jobs/{jobId}`

• odczyt pliku joba
• zwrot statusu
• jeśli Completed → zwrot wyniku


---
